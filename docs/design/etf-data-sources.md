# ETF 工具上游调研（`etf`）

> 回答的问题：**「全市场 ETF 有多少、多大、现在贵不贵（折溢价）、跟踪的是什么指数？」**
> 本文只记录**上游接口的逆向结论**（字段、参数、实测数字、坑）；
> 领域模型与展示方案见 [`etf-tool.md`](./etf-tool.md)。

调研时间：**2026-09-22**（周二，收盘后 / 盘中各测了一轮）。所有数字均为实测，非推测。

---

## 0. 结论摘要

| 需要的信息 | 来源 | 请求数 | 频率 |
|---|---|---|---|
| 行情 + 折溢价/上市日 + 量比/主力净流入（**默认源**） | `push2.eastmoney.com/api/qt/ulist.np/get`（**接口 A′**，按代码池批量报价，100 只/请求） | 17（1675 行） | 交易时段每 30 分钟 |
| 同上，但**自带代码池**（目录不可用时的东财兜底） | `push2.eastmoney.com/api/qt/clist/get`（**接口 A**，按板块翻页） | 17（1623 行 ÷ 100/页） | 仅在需要兜底时 |
| 行情（价格/涨跌/成交额/换手/规模，无折溢价；**兜底源**） | 新浪 `Market_Center.getHQNodeData?node=etf_hq_fund`（**接口 A″**，列表自带代码池） | 17（1676 行 ÷ 100/页） | 仅在降级时 |
| 跟踪指数 + ETF 分类 + 区间涨跌 + 1 年最大回撤 | `datacenter-web.eastmoney.com/api/data/v1/get?reportName=RPT_FUND_ETFLIST`（**接口 B**） | 2（1675 行 ÷ 1000/页） | 每日 |
| 单只基金的费率/规模/管理人/成立日（详情抽屉） | `fundmobapi.eastmoney.com/FundMNewApi/FundMNDetailInformation`（**接口 C**） | 1/只（按需 + 落库缓存） | 用户下钻时 |
| **反查场外联接基金**（ETF → 场外） | 候选池 = **接口 E**（`fundcode_search.js`）+ `FundMNewApi/FundMNInverstPosition`（**接口 I** 反查 `ETFCODE`） | 首次 **≈2320**（≈4 分钟）；之后增量几十个 | 周级（见 §8.4） |

**不用 `clist`，但也没放弃东财**：2026-09-22 实测（见 §7），东财把**按板块翻页的 `clist`**
按接口重置了（主备域名 + 多台集群一样，失败前还要退避重试两轮）；
而同一批域名上的 **`ulist.np/get`（按代码批量报价）完全正常**，字段与 `clist` 完全一致。
因此默认走 `ulist.np`（代码池取自目录接口 B），`clist` 只留作「目录也挂了」时的东财兜底，
新浪则是两个东财接口都失败后的兜底。

**折溢价只有东财给**：`f402`（折溢价率）**没有免费替代**（§7.2），因此默认行情优先走东财
（**走 `ulist.np` 而不是被重置的 `clist`**，见 §7.4），失败自动降级回新浪；
用户可以在界面上切换到「只走新浪」（偏好存 `app_setting` 表）。
响应的 `dataSource.missing` 会显式列出当前渠道缺哪些字段，前端据此隐藏折溢价相关视图，
避免把「缺失」渲染成「平价」。

实测（2026-09-22 晚，默认链路）：**1675 只 / 约 6 秒 / 折溢价齐全**
（未知 0、高溢价 36、溢价 288、平价 754、折价 594、高折价 3，最贵 159509 纳指科技ETF景顺 +27.74%）。

**没有**任何单一接口同时给出行情与跟踪指数 —— 因此本工具是「行情接口 × 接口 B 按代码 join」，
并允许 B 失败时降级（分类回退到名称判定，见设计文档）。

## 1. 接口 A：场内 ETF 行情（`clist`）

```
https://push2.eastmoney.com/api/qt/clist/get
  ?pn=1&pz=100&po=1&np=1&fltt=2&invt=2
  &fid=f20                     # 排序字段（f3 涨跌幅 / f20 规模 …）
  &fs=b:MK0021,b:MK0022,b:MK0023,b:MK0024,b:MK0827   # 板块过滤
  &fields=f2,f3,f4,f5,f6,f7,f8,f10,f12,f13,f14,f15,f16,f17,f18,f20,f21,f22,f26,f62,f124,f402
```

### 1.1 板块取值（`fs`）实测

| `fs` | 含义（实测样本推得） | 条数 |
|---|---|---|
| `b:MK0021` | 股票型 ETF（沪深） | 1338 |
| `b:MK0022` | 货币 ETF | 27 |
| `b:MK0023` | 跨境 ETF（QDII） | 241 |
| `b:MK0024` | 商品 ETF（黄金 10 只） | 10 |
| `b:MK0827` | 商品 ETF 全集（黄金 14 + 豆粕/有色/能源化工 3） | 17 |
| 上表五者并集 | **全市场 ETF** | **1623** |
| `b:MK0025`/`MK0026`/`MK0027`/`MK0028`/`MK0404` | LOF / 分级，**不是 ETF** | — |

- 实测 `MK0024 ⊂ MK0827`（10 只黄金 ETF 同时命中两者），
  所以取并集后是 1623 而不是 1633 —— 采集端必须按代码去重。
- `m:1+b:MK0021` = 745（沪市）、`m:0+…` 可分离深市；但**不必**拆板块请求，
  行内 `f13` 已经给了市场（1 = 沪市，0 = 深市）。

### 1.2 字段语义（含实测样例）

500 行样本 `< 12 行裁剪版` 见 `packages/sources/test/fixtures/eastmoney/etf-spot/boards.json`。

| 字段 | 含义 | 单位/样例 |
|---|---|---|
| `f12` | 代码 | `510300` |
| `f14` | 简称 | `沪深300ETF华泰柏瑞` |
| `f13` | 市场 | `1` 沪 / `0` 深 |
| `f2` `f18` `f15` `f16` `f17` | 最新价 / 昨收 / 最高 / 最低 / 今开 | 元 |
| `f3` `f4` | 涨跌幅 % / 涨跌额 | `3.55` / `0.05` |
| `f5` `f6` | 成交量（手）/ 成交额（元） | `114941` / `16845295` |
| `f7` `f8` `f10` `f22` | 振幅 % / 换手率 % / 量比 / 涨速 % | |
| `f20` `f21` | 总市值 / 流通市值（≈ **场内规模**，元） | 510300：`109391241858`（1093.9 亿） |
| `f26` | **上市日期** | `20120528` |
| `f62` | 主力净流入（元） | |
| `f124` | 行情时间戳（秒） | `1790064693` → 2026-09-22 16:11 |
| `f402` | **`−溢价率`（%）** | `0.06` = 折价 0.06% |

> **`f402` 的符号约定与 `packages/sources/src/eastmoney/quote.ts` 完全一致**：
> `f402 = (净值 − 价格) / 净值 × 100`，负值代表**溢价**。
> 实测 510300：`f2 = 4.613`、`f402 = 0.06` → 净值 ≈ 4.6158，折价 0.06%。
> 归一化到对外字段时取反（`premiumRate = −f402`），让「正 = 溢价」与中文语义一致。

> **`fltt=2` 必须带**：不带时数值按 ×100 / ×1000 缩放
> （同一个 510300：`f2=4613`、`f402=6`），会在前端渲染出 1000 倍的价格。

### 1.3 分页：`pz` 上限实测 100

| `pz` | 实际返回行数 |
|---|---|
| 100 / 200 / 500 / 1000 / 2000 | **100**（全部被截断到 100） |

因此全市场 1623 只必须翻 **17 页**（`pn=1..17`，`pz=100`）。
翻页终止条件用「本页返回行数 < 100」或「已收集 ≥ `data.total`」，
并对 `data.total` 做上限护栏（> 5000 直接 `ParseError`，避免上游异常导致无限翻页）。

### 1.4 主备域名与限流（**重要**；该渠道已从默认链路移除）

| 域名 | 实测 |
|---|---|
| `push2.eastmoney.com` | 正常可用；短时间内高频访问后会被**静默重置 TLS**（`SSL_read: unexpected eof`），curl 与 Node 均命中 |
| `push2delay.eastmoney.com` | 延时行情，备用域名，`fs=b:MK0021` 只回 1338（少了跨境/商品板块） → **只能当兜底**，不能当主源 |

实测经验：同一 IP 连续 30+ 次请求后主域名开始拒绝连接，冷却数分钟后恢复；
`quote.ts` 早已采用「主域名 → 备用域名」的自动切换，本工具复用同一策略。

但**限流会升级成 IP 级封禁**：2026-09-22 下午调研结束后，`push2` / `1.push2` / `7.push2` /
`21.push2` / `push2his` / `push2delay` 对本机**全部** `UND_ERR_SOCKET`（连 TCP 都建不起来，
HTTP 与 HTTPS 表现一致），持续 40+ 分钟未恢复；而同一台机器上 `datacenter-web`（接口 B）与
`fundmobapi`（接口 C）完全正常 —— 说明限流只打行情集群，且**主备域名同生共死**（见 §7）。

**处置（2026-09-22）**：封禁反复出现且代理出口 IP 与直连相同（换 IP 无效），
因此把行情主源换成新浪（§7.1），`clist` **默认不再调用**；
只在「目录不可用、`ulist.np` 拿不到代码」时作为东财兜底，且失败降级回新浪。
本节的限流结论保留，作为「为什么不用它」的证据。

**收盘后复测补充（重要，见 §7.4）**：封禁是**按接口**而不是按域名的 ——
`clist`（列表）在全部 push2 域名上被重置，同一个域名上的 `ulist.np/get`（批量报价）却完全正常，
且返回**同样的 21 个字段**（含 `f402` 折溢价 / `f26` 上市日）。

## 2. 接口 B：ETF 目录（跟踪指数 + 分类）

```
https://datacenter-web.eastmoney.com/api/data/v1/get
  ?reportName=RPT_FUND_ETFLIST&columns=ALL&pageSize=1000&pageNumber=1
  &sortColumns=SECURITY_CODE&sortTypes=1
```

- 实测 `count = 1675`、`pageSize` 上限 1000 → **2 页**取全（`pages = 2`）。
- 返回 1675 行 ⊇ 接口 A 的 1623 只：多出来的是**已成立未上市**（无场内行情）的新 ETF，
  例如 `158000 港股通金融ETF鹏华`。工具以「有行情」为准，未上市的在统计里单列。

| 字段 | 含义 |
|---|---|
| `SECURITY_CODE` / `SECURITY_NAME_ABBR` / `SECUCODE` | 代码 / 简称 / `510300.SH` |
| `INDEX_CODE` / `INDEX_NAME` | **跟踪指数**代码（`000300`、`H11146`）与名称（`沪深300`）|
| `DERIVE_INDEX_CODE` / `TRACKINDEX_QUOTES_CODE` | 指数行情代码（`000300.SH` / `000300.2`）|
| `DEC_NAV` / `DEC_TOTALSHARE` | **规模（亿元）/ 份额（份）** —— 见下方交叉验证 |
| `CHANGE_RATE_1W` / `_1M` / `_3M` / `YTD_CHANGE_RATE` | 近 1 周 / 1 月 / 3 月 / 年初至今涨跌（%）|
| `MAXDRAWDOWN1Y` | 近 1 年最大回撤（%，负值）|
| `IS_*ETF` | 分类标志位，见 2.2 |

### 2.1 `DEC_NAV` 是「规模（亿元）」而不是「净值」—— 三处交叉验证

| 代码 | `DEC_NAV` | `DEC_TOTALSHARE` | 相除得单价 | 与行情对照 |
|---|---|---|---|---|
| `510300` | 1093.699 | 23,713,687,700 | 4.613 元 | 与 `f2 = 4.613` 一致 |
| `513100` | 189.558 | 9,552,110,600 | 1.985 元 | 与基金净值 1.9831 一致 |
| `511990` | 967.251 | 967,251,000 | **100** 元 | 货币 ETF 场内面值 100 元 |
| `159985` | 35.251 | 1,579,924,066 | 2.231 元 | 与豆粕 ETF 价格一致 |

且 `510300` 的 `DEC_NAV ≈ f20 / 1e8`（1093.7 亿 vs 1093.9 亿）。
**结论**：`DEC_NAV` 单位是亿元、含义是「价格 × 份额」的规模估算；
本工具以接口 A 的 `f20` 为主、`DEC_NAV` 作为缺失时的回退。

### 2.2 `IS_*ETF` 标志位语义（逐个人工核对样本）

| 标志位 | 含义 | 为 1 的行数 | 抽样证据 |
|---|---|---|---|
| `IS_HBETF` | 货币 | 27 | `159001 货币ETF易方达`、`511990 华宝添益ETF`（与 `MK0022` 的 27 完全吻合）|
| `IS_WPETF` | 跨境 | 246 | `513100 纳指ETF国泰`、`159010 港股通科技ETF博时` |
| `IS_ZQETF` | 债券 | 53 | `159110 科创债ETF万家`、`159111 科创债ETF天弘` |
| `IS_SPETF` | 商品 | 17 | `159985 豆粕ETF华夏`、`518880 黄金ETF华安`（与 `MK0827` 的 17 完全吻合）|
| `IS_KJETF` | **宽基** | 373 | `510300 沪深300...`、`159337 中证500ETF东财`、`159215 A500ETF平安`、`159247 创业板ETF汇添富` |
| `IS_HYETF` | **行业主题**（HangYe） | 812 | `512880 证券ETF国泰`、`158010 医疗ETF嘉实` |
| `IS_FGETF` | **风格**（FengGe） | 189 | `158023 红利低波ETF万家`、`159021 大盘价值ETF华夏` |
| `IS_HSETF` / `IS_HSMARKET` | 沪深（境内）市场 | 1332 / 1492 | 跨境行为 0 |

- **`IS_HBETF`…`IS_HYETF` 六者互斥**（实测无一行同时命中两个），构成一个完整划分：
  `27 + 246 + 53 + 17 + 373 + 812 = 1528`，其余 147 行只命中 `IS_FGETF`（风格）。
- `IS_FGETF` 是**叠加维度**：有 42 行同时命中「宽基/行业主题」。工具里把它排在
  宽基/行业主题**之前**（先风格后宽基），具体优先级见设计文档 §3.1。
- 推断依据是「标志位缩写 = 中文分类拼音首字母」+ 样本核对；**没有官方文档**，
  因此解析层保留原始四个分类字段的布尔值，分类优先级放在 `core`（可测、可改）。

## 5. 请求预算（克制原则）

- **每次快照 19 个请求**（行情主源 17 页 + 目录 B 2 页），约 2 MB
  —— 换源前后请求数**不变**（新浪与 push2 的 `num`/`pz` 上限同为 100），
  所以这次换源只降低「被限流/失败重试」的风险，不增加上游压力；
- 定时任务只在**交易时段**跑：`*/30 9-15 * * 1-5` → 每天 14 次 ≈ **266 请求/天**；
  收盘后不再重复打上游（最后一次 15:30 已包含当日收盘价）。
- 接口 C 只在用户点开详情抽屉时调用，并按 `code` 落库缓存。

> 备选腾讯 `qt.gtimg.cn` 一次可拿 500 只（**4 次请求**拿全市场），但缺折溢价/上市日，
> 且要额外维护「目录代码池 → 行情」的拼装；当前 266 请求/天的量远未触到新浪的限流阈值，
> 暂不引入第三种口径（见 §7.3）。

## 6. 实测发现与风险（2026-09-22）

| 项 | 实测 | 结论 |
|---|---|---|
| 全市场 ETF（接口 A 并集） | **1623 只** | 与 `MK0021+MK0022+MK0023+MK0024` 的 1616 相比，补上 `MK0827` 的 7 只非黄金商品 ETF |

## 7. 行情渠道调研与选型（push2 封禁期间实测）

调研缘起：当天下午 push2 **整个家族**对本机 IP 封禁（见 §1.4），只剩接口 B / C 可用 ——
正好借这个窗口把「能不能不依赖 push2」测清楚。

**结论：行情主体有更省请求的替代品，但折溢价率仍然只有东财给。**

### 7.1 能提供全市场行情的渠道

基准代码池取自新浪全量列表：**1676 只**（17 页 × 100 行，第 18 页为空），再用同一批代码验证各渠道覆盖率。

| 东财 `push2 ulist.np`（**默认源**） | 100 只/请求 | 17 次 | 与 `clist` 完全同字段 | 需要先有代码池（目录接口 B） |

覆盖率与口径交叉验证（均为实测）：

- 腾讯 9 次批量（200 只/次）返回 **1676/1676 行**；新浪 17 页共 **1676 行**；
  两边都命中 `511990`（货币）/ `513100`（跨境）/ `159985`（商品）/ `588000` / `159915`。
- 规模口径：腾讯「总市值」510300 = **1093.91 亿**，与接口 A 的 `f20`（1093.91 亿）一致；

  但新浪 `mktcap`（总市值）对货币 ETF 与 `f20` 不一致（511990：783 亿 vs 967 亿）—— 映射要取 `nmc`。
- **单位与口径不能按字段名对齐**：新浪 `amount` 是元、`volume` 是股（接口 A 的 `f5` 是手）；
  腾讯成交额是万元、总市值是亿元；腾讯「换手」与接口 A 的 `f8` 口径也不同（同一只 510300：2.72 vs 0.27）。

### 7.2 折溢价率（`f402`）没有等价替代

| 候选 | 实测结果 |
|---|---|
| 腾讯行情（88 个字段） | 逐字段核对，无 IOPV / 折溢价 |
| 新浪两个行情接口（20 / 33 个字段） | 无折溢价 |
| 雪球 / 集思录 / 交易所 / 百度 / 网易 | 见 §4：要么需登录、要么只有元数据、要么根本没有这个字段 |

**唯一近似**是 `价格 ÷ 单位净值 − 1`，腾讯 `q=jj510300` 一次就给「单位净值 + 净值日期」：

| 代码 | 价格 | 单位净值（净值日） | 差额 | 判定 |
|---|---|---|---|---|
| 510300 | 4.613 | 4.6179（2026-09-22，T 日） | −0.11% | 与其 IOPV 口径接近，可用 |
| 159985 | 2.323 | 2.2438（2026-09-22） | +3.5% | 收盘后口径，量级合理 |
| 513100 | 2.316 | 2.0503（2026-09-21，**T-1**） | **+12.9%** | 跨境 ETF 的 T-1 净值 + 隔夜指数涨跌把「溢价」放大一个数量级 |

→ 因此**不要**用净值近似静默填充折溢价：它是日频、T-1 口径，对跨境 ETF 会给出完全错误的信号。

### 7.3 已实现的渠道策略（默认东财，界面可切）

1. **默认优先东财**（`eastmoney`），按下面的顺序取数（`service.ts` 的 `fetchSpot`）：
   - 有代码池（目录接口 B 的 1675 行）→ **`ulist.np` 批量报价**（`packages/sources/src/eastmoney/etf-quotes.ts`，
     100 只/请求 = 17 次，含折溢价/上市日/量比/主力净流入/行情时间戳）；
   - 没有代码池（目录挂了）→ `clist` 按板块翻页（自带代码池）；
   - 两者都失败 → 新浪；
   —— 所以最坏结果是「降级成新浪」，而不是数据集挂掉；
2. **新浪**（`packages/sources/src/sina/etf-spot.ts`）：17 页拿回 1676 只的
   价格/涨跌/成交额/换手/规模，**自带全市场代码池**，因此它是东财任何一步失败后的兜底；
   缺的字段（折溢价率/上市日期/主力净流入/量比）**显式声明**在 `ETF_SPOT_SOURCES`（`packages/shared`）里；
3. **渠道可以在界面上切**（`GET/PUT /api/tools/etf/config`）：偏好存 `app_setting` 表，
   切换后立刻重抓一次；`ETF_EASTMONEY_ENABLED` 只是「没切换过」时的默认值；
4. **实际用了哪个渠道以数据库为准**：`etf_spot_daily.source` 落库（迁移 0006），
   数据集响应里的 `dataSource` 由当日行的**多数派**反推 —— 进程重启、缓存清空后依然判断正确，
   不会出现「上次降级了但界面还写着东财」；
5. **目录成了代码池，因此目录的完整性被加了护栏**：`fetchEtfProfiles` 现在比对
   `count` 与实际行数（低于 90% 直接 `ParseError`）—— 少一页就等于数据集少一批标的，
   宁可让上层降级到新浪，也不能悄悄交出残缺快照；
6. **缺失 ≠ 0**：`premiumRate` 置 `null`、文案 `—`，`stats.premium.unknown === total`，
   前端隐藏折溢价筛选/分布/榜单（而不是画一排 0）；这条有端到端断言（`pnpm smoke`）。

**没有实现的备选**：腾讯行情（4 次请求拿全市场）留作第三渠道 —— 它同样没有折溢价，
收益只是「请求数更少」，在 266 请求/天的量级下不划算（§5）。

### 7.4 复测：封禁是按**接口**的（`clist` ✗ / `ulist` ✓）

收盘后（2026-09-22 晚）逐个接口复测，推翻了「整家族 IP 封禁」的粗判：

| 请求 | 结果 |
|---|---|
| `push2.eastmoney.com/api/qt/clist/get`（列表） | ✗ 111ms `other side closed` |

| `push2delay…/ulist.np/get` | ✓ 200，117ms |

`ulist.np/get` 传 `fields=f2,f3,f4,f5,f6,f7,f8,f10,f12,f13,f14,f15,f16,f17,f18,f20,f21,f26,f62,f124,f402`

> 这解释了为什么 QDII 工具的「场内溢价」在本次故障期间一直正常：
> 它走的就是 `ulist.np/get`（见 `packages/sources/src/eastmoney/quote.ts`），不是 `clist`。

**已实现并成为默认链路**（见 etf-tool.md §4 与 §10）：
**代码池（目录接口 B，2 请求）+ `ulist.np/get` 分批报价（17 请求）**，
请求数与新浪链路完全相同（19），却拿回了含折溢价的全字段。
两个已验证的前提：

- 目录 B 的 **1675 个代码全部命中报价**（1675/1675），因此「按代码池报价」不会漏标的；
  新浪有而 B 没有的只有 1 个（`512390`，ulist 也不回报价 —— 已退市/停牌）；
- 端到端实测：1675 只、约 6 秒、`premiumRate` 全部有值（见 §7.3 的数字），`pnpm smoke` 50/50 通过。

仍然存在的耦合：**用东财时数据集的口径 = 目录 B 的代码池**（新浪链路不受影响）。
目录若被上游截断，护栏会拦下来（§7.3 第 5 条）；界面上切到新浪即可完全绕开这个耦合。

## 8. 反查：ETF → 场外联接基金（2026-09-22 实测）

> 回答的问题：**「这只 ETF 对应的场外基金（联接基金）有哪些？」**
> 注意方向：QDII 工具里的接口 I 是**场外 → 场内**（联接基金 → 它持有的 ETF，见 qdii-data-sources.md §「`ETFCODE`」），
> 本节要的是**场内 → 场外**，不是同一个查询。

### 8.1 没有现成的批量字段（三个方向都试过）

| 尝试 | 实测结果 |
|---|---|
| 接口 B 全字段 `columns=ALL` | **只有 25 列**，无 `FEEDER_*` / `LINK_*` / 联接类字段（字段清单见 §2） |
| 数据中心报表猜测（`RPT_FUND_ETFLINK` / `LINKFUND` / `ETFLIANJIE` / `FEEDER` / `INDEX` / `RPT_INDEX_FUND` …） | 全部 `报表配置不存在`（只有无关的 `RPT_FUND_RELATION` 存在，返回的是板块，18 行） |
| 接口 C `FundMNDetailInformation` 的 ETF 侧 | 有 `INDEXCODE` / `INDEXNAME` / `BENCH`，**没有**联接基金字段 |

联接基金的**跟踪指数字段与 ETF 目录的口径不一致**（`270042.INDEXCODE=NDX100` vs
`159941.INDEX_CODE=NDX`），所以「按指数 join」也不是免费的（要先做指数代码映射），本节不采用。

### 8.2 采用的方案：全量「联接」基金目录 × 接口 I 反查

两步，都是既有接口：

1. **候选池（1 请求）**：`https://fund.eastmoney.com/js/fundcode_search.js`
   → 全市场 **27905** 只基金（`[代码, 拼音缩写, 名称, 类型, 全拼]`），
   取名称含「联接」的 **2319** 只（其中含 `ETF` 的 **2269** 只，`发起式联接` 975 只）。
   该文件曾被 §4 判为「不需要」，但这里正是它的用武之地：**一次请求拿到全部候选，无需搜索接口**。
2. **反查（每只 1 请求）**：接口 I `FundMNInverstPosition?FCODE=<联接代码>`
   → `Datas.ETFCODE` / `Datas.ETFSHORTNAME`。实测该接口对「空仓」的联接基金也稳定返回目标 ETF，
   并带 `Expansion`（持仓报告期，如 `2026-06-30`）。

**全量实测**（两次，分别用探测脚本与**应用内**的正式链路）：

| 指标 | 探测脚本（20 并发，无间隔） | **应用内**（6 并发 / 100ms，见 §8.4） |
|---|---|---|
| 耗时 | 3.7 秒 | **232.7 秒**（≈4 分钟） |
| 候选 / 映射 | 2319 → 2306（0 失败） | 2317 → **2304**（**0 失败**） |
| 空结果 | 13 只（新成立、尚未建仓） | 13 只 |
| 反查到的 ETF | 1021 只，全部命中接口 B 的 1675 只目录 | **1020 只**（名单本身在变） |
| 目录覆盖率 | 61.0% | **60.9%** |

> 两次候选数不同（2319 / 2317）说明**候选池本身每天都在变**（新基金成立、简称修订），
> 所以「覆盖率」是个会漂移的实测值，不是常量。
> 其余 654 只没有联接基金的是债券/商品/部分跨境主题 —— 它们本来就没有场外份额。

**多份额样例**：159941 → `000055, 006479, 006480, 021778, 270042`；
510300 → `006131, 022699, 022948, 460300`（A/C/I/Y）。

> 该接口**未触发任何限流**（不像 `clist`）；但仍是 2300+ 请求量级，
> 必须**落库快照 + 定期刷新**，绝不能进用户请求路径。

### 8.3 轻量备选：单只 ETF 的直链（不采用为唯一口径）

`https://fund.eastmoney.com/<ETF代码>.html` 的标题栏有硬编码直链：

```html
<a style='float: right;' href="http://fund.eastmoney.com/270042.html">查看相关ETF联接></a>
```

- 优点：**每只 ETF 只要 1 个请求**，无需扫全量目录；
- 缺点：**只给 1 只「主」份额**（159941 指到 270042，`000055/006479/006480/021778` 全丢），
  且要爬 HTML 的 `float: right` 样式定位，与 §4 判 `jbgk` 不采用的理由相同（HTML 脆弱）。
- 结论：可作**单只下钻的兜底**，但全量口径仍用 §8.2。

### 8.4 代价与取舍（已实现：见 etf-tool.md §11）

- **一次全量刷新 ≈ 2320 请求**，对比行情链路 19 请求/次 —— 高出两个数量级。
  实现上给了它一条**专用 HTTP 通道**（6 并发 / 同 host 100ms = 10 req/s），
  实测 232.7 秒跑完全量、**零失败零限流**；共用通道（2 并发 / 300ms）会把同样的量
  拖到 12 分钟。100ms 的间隔相对实测（20 并发 3.7 秒）留了 50 倍余量。
- **稳态不靠全量**：落库表里已有的联接基金不再重查（增量只补「候选池里的新代码」
  与「上次没查到的代码」），因此周任务通常只有几十个请求；
  全量只用于首次建库与手动重建（清理已清盘的联接基金）。
- 候选池复用**接口 E**（`fund-list.ts`，2.3 MB）—— 本工具不需要新的目录接口。
- 联接基金的**净值/费率**（用户真正关心的申购信息）走接口 C 按需取，不在这次快照里；
  界面里只给代码 + 外链。
